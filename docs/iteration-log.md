## 1. 架构统一：共享渲染模块体系

### 问题描述

联机模式下，主机玩家（P1）和成员玩家（P2/P3/P4）看到的画面完全不同：
- P1 看到的是美化后的版本（精致坦克、金色星星基地、蓝色水）
- P2 看到的是古老版本（简单方块坦克、绿色十字基地、绿色水）

### 根本原因

**架构错误**：`RemoteView`（成员端视图）自己实现了一整套独立的渲染逻辑，与主机端游戏对象渲染完全分离。每次新增美化元素都要写两套，容易产生分歧。

成员端不是"加入同一个世界"，而是"被分配了另一套简化版游戏"。

### 修复方案

**正确架构**：把所有游戏元素渲染提取为独立共享模块，主机端和成员端都调用同一个。`RemoteView` 只负责把快照数据转换为渲染模块需要的参数，不包含独立渲染逻辑。

**两个玩家的区别只应该在控制系统**（绑定的角色、网络输入），**游戏资产方面应该是完全共通的体系**，不应该产生分歧。

### 共享模块清单

| 模块 | 文件 | 渲染内容 |
|------|------|---------|
| `MapVisual` | `src/ui/MapVisual.ts` | 地图瓦片（6生物群系/8种瓦片/动态效果/4分块砖墙） |
| `TankVisual` | `src/ui/TankVisual.ts` | 坦克（玩家P1/P2/敌方6级差异化/影子/排气口） |
| `BaseVisual` | `src/ui/BaseVisual.ts` | 基地（金色星星/护墙/HP条/修复特效） |
| `EntityVisual` | `src/ui/EntityVisual.ts` | 掉落物/道具/子弹（火焰/激光/地雷/炸药包） |
| `MenuVisual` | `src/ui/MenuVisual.ts` | 菜单（背景/标题/选项/暂停/设置行） |
| `VisualTheme` | `src/ui/VisualTheme.ts` | 颜色主题/渐变/发光/面板/按钮/槽位/进度条 |

### 修改的文件

- 新增：`src/ui/MapVisual.ts`、`src/ui/TankVisual.ts`、`src/ui/BaseVisual.ts`、`src/ui/EntityVisual.ts`、`src/ui/MenuVisual.ts`、`src/ui/VisualTheme.ts`
- 修改：`src/game/Tank.ts`、`src/game/Tilemap.ts`、`src/game/Base.ts`、`src/systems/loot/LootSystem.ts`、`src/systems/powerup/PowerUpSystem.ts`、`src/systems/combat/CombatSystem.ts`、`src/ui/RemoteView.ts`

### 对 Cocos/Unity 版的参考建议

- **必须统一渲染管线**：主机端和客户端应该使用同一套渲染代码，不应该为客户端单独写简化版渲染。
- **客户端只负责数据转换**：把网络快照数据转换为渲染组件需要的参数，然后调用同一套渲染组件。
- **新增元素只写一次**：所有游戏元素的渲染逻辑应该是共享的，主机端和客户端都调用同一个。

## 2. 联机同步：地图状态增量同步

### 问题描述

2号玩家攻击砖块，砖块的碰撞会消失（玩家可以通过），但是显示还在。这是以前修复过的bug又出现了。

### 根本原因

`RemoteView` 的地图只在**首帧加载**（`if (s.map && s.map !== this.lastMap)`），后续快照不带 `map` 字段（为了节省带宽），所以地图状态**永远不会更新**。

主机端的地图变化（砖块被打掉、临时墙放置等）不会反映在2号机上。

### 修复方案

**地图增量同步**：只发送变化的瓦片，带宽消耗极小。

1. **`Tilemap` 添加变化跟踪**：
   - `dirtyTiles: Set<number>` — 变化的瓦片索引集合
   - `set()` 方法中自动记录变化的瓦片
   - `getDirtyTileChanges()` — 获取变化列表 `Array<{col, row, type}>`
   - `clearDirtyTiles()` — 发送后清空

2. **`NetSnapshot` 添加字段**：
   - `mapChanges?: Array<{col, row, type}>`

3. **`OnlineHostMode.buildSnapshot`**：
   - 添加 `mapChanges` 字段，只发送变化的瓦片
   - 发送快照后调用 `tilemap.clearDirtyTiles()`

4. **`RemoteView.setSnapshot`**：
   - 应用 `mapChanges`，更新本地地图和缓存

### 修改的文件

- `src/game/Tilemap.ts` — 添加 `dirtyTiles` 变化跟踪
- `src/net/NetTypes.ts` — 添加 `mapChanges` 字段
- `src/modes/OnlineHostMode.ts` — 构建快照时添加 `mapChanges`，发送后清空
- `src/ui/RemoteView.ts` — 应用 `mapChanges`

### 对 Cocos/Unity 版的参考建议

- **地图状态必须同步**：不能只在首帧发送完整地图，后续不更新。
- **增量同步是最佳实践**：只发送变化的瓦片，带宽消耗小，实时性好。
- **变化跟踪要自动化**：瓦片 `set()` 方法中自动记录变化，不需要手动标记。

## 3. 联机同步：生物群系（biome）同步

### 问题描述

1号玩家看到的水是蓝色的，2号玩家看到的水是绿色的。坦克颜色也不同（1号蓝、2号绿）。

### 根本原因

生物群系（biome）同步有bug：
- `RemoteView.setSnapshot` 中，`biome` 只在 `s.map` 存在时才同步
- `OnlineHostMode.buildSnapshot` 中，`biome` 只在首帧发送（`this.mapSent ? undefined : ...`）
- 后续增量快照不带 `map`，所以 `biome` 永远不会被同步！
- 2号玩家使用默认的 `classic` 生物群系（蓝色水），而1号玩家可能是 `swamp`（绿色水）

### 修复方案

1. **`RemoteView.setSnapshot`**：把 `biome` 同步移到 `s.map` 判断之外，确保每次快照都能同步
2. **`OnlineHostMode.buildSnapshot`**：把 `biome` 改为每帧都发送（只是一个字符串，带宽消耗很小）

### 修改的文件

- `src/modes/OnlineHostMode.ts` — `biome` 每帧都发送
- `src/ui/RemoteView.ts` — `biome` 同步移到 `map` 判断之外

### 对 Cocos/Unity 版的参考建议

- **全局配置必须每帧同步**：生物群系、天气、时间等全局配置应该每帧都发送（数据量小），不能只在首帧发送。
- **同步逻辑不应该依赖其他字段**：`biome` 的同步不应该依赖 `map` 字段是否存在。

## 4. 联机同步：成员端输入处理

### 问题描述

2号玩家不能移动，移动后瞬间被拉回原地。敌方坦克也不移动，整个游戏静止。

### 根本原因

`consumeRemoteInputQueue` 的实现有问题：
- 原来使用固定60Hz步进处理远程输入队列
- 队列积压或时序问题导致输入被错误应用
- 2号玩家的移动输入没有被正确应用到游戏逻辑中

### 修复方案

**简化输入处理**：每帧直接应用队列中最新的远程输入。

```typescript
// 简化后的逻辑
consumeRemoteInputQueue(): void {
  if (this.remoteInputQueue.length === 0) return;
  // 取最新的输入
  const latest = this.remoteInputQueue.pop();
  if (latest) {
    this.input.setOverrideP2(latest.flags);
  }
  // 清空队列（避免积压）
  this.remoteInputQueue.length = 0;
}
```

### 输入接收路径

```
成员发送 input 消息
  → 服务器转发为 peer_input 消息给主机
  → net.on("peerInput")
  → host.enqueueRemoteInput()
  → consumeRemoteInputQueue()
  → input.setOverrideP2()
```

### 修改的文件

- `src/modes/OnlineHostMode.ts` — 简化 `consumeRemoteInputQueue`

### 对 Cocos/Unity 版的参考建议

- **输入处理要简单可靠**：不要使用复杂的队列步进逻辑，每帧直接应用最新输入即可。
- **避免队列积压**：应用最新输入后清空队列，避免积压导致延迟。
- **输入覆盖要明确**：成员端输入应该覆盖本地P2输入，不能让本地小键盘和远程输入冲突。

## 5. 视觉修复：坦克影子方向

### 问题描述

坦克的影子会随着朝向变化，有时在左边、上边、右边。这是错误的，影子应该有固定的光源方向。

### 根本原因

影子是在 `ctx.rotate(angle)` **之后**绘制的，所以影子会随着坦克朝向旋转。

### 修复方案

**影子必须在旋转之前绘制**，确保影子方向固定（光源在左上方，影子在右下方），不随坦克朝向变化。

1. **`TankVisual`**：
   - 导出独立的 `drawTankShadow(ctx, w, h)` 函数
   - 影子位置固定在右下方（`w/4+2, h/4+2`）
   - 从 `drawTankBody` 中移除影子绘制

2. **`Tank.ts`（主机端）和 `RemoteView.ts`（成员端）**：
   - 在 `ctx.translate()` 之后、`ctx.rotate()` 之前调用 `drawTankShadow`

### 修改的文件

- `src/ui/TankVisual.ts` — 导出 `drawTankShadow`，从 `drawTankBody` 移除影子
- `src/game/Tank.ts` — 旋转之前绘制影子
- `src/ui/RemoteView.ts` — 旋转之前绘制影子

### 对 Cocos/Unity 版的参考建议

- **影子是世界空间的，不是物体空间的**：影子应该在世界坐标系中绘制，不应该随物体旋转。
- **固定光源方向**：所有物体的影子都应该朝向同一个方向（如右下方），模拟固定光源。
- **2D游戏中影子的正确做法**：先在世界坐标绘制影子，再旋转物体绘制本体。

## 6. 视觉修复：屏幕震动反馈

### 问题描述

击中敌人的时候也会屏幕震动。屏幕震动应该是负反馈，只有**被攻击**和**基地被攻击**的时候才会出现，不应该在主动击中敌人的时候出现。

### 根本原因

`spawnExplosion` 和 `spawnExplosionAt` 中无条件触发屏幕震动，没有区分是玩家受伤还是敌人受伤。

### 修复方案

- `spawnExplosion`：只在玩家受伤时才震动
- `spawnExplosionAt`：移除震动（这个函数用于敌人爆炸等场景）
- `DroneSystem.explodeAt`：移除震动

### 修改的文件

- `src/systems/combat/CombatSystem.ts` — 震动修复
- `src/systems/drone/DroneSystem.ts` — 移除震动

### 对 Cocos/Unity 版的参考建议

- **屏幕震动是负反馈**：只在玩家受伤、基地受损等负面事件时触发。
- **正面反馈用其他方式**：击中敌人可以用命中特效、伤害数字、音效等，不应该用屏幕震动。
- **震动强度要区分**：玩家受伤震动强，基地受损震动中等，其他事件不震动。

## 7. 地图地形：水面与连通性检验

### 问题描述

水面生成不合理，可能把玩家和敌军完全隔断开，导致游戏无法进行。

### 修复方案

1. **水面改为块状生成**：2x2/3x3块状，而不是零散的单格
2. **新增连通性检验**：`verifyConnectivity` 函数（BFS洪水填充），确保：
   - 怪物出生点到玩家之间有通道
   - 玩家不会被完全堵死
   - 岩石和海面不会完全阻断（砖墙是可破坏地形，没问题）

### 修改的文件

- `src/systems/terrain/MapGenerator.ts` — 水面块状生成 + 连通性检验

### 对 Cocos/Unity 版的参考建议

- **地图生成后必须验证连通性**：确保所有关键位置（玩家出生点、敌人出生点、基地）之间有通路。
- **不可破坏地形不能阻断通路**：岩石、水面等不可破坏地形不能把地图完全分割。
- **BFS洪水填充是标准算法**：从玩家出生点开始洪水填充，检查所有关键位置是否可达。

## 8. 地图地形：移除毒雾绿泡泡

### 问题描述

地图上有一个起绿泡泡的地形，一直在突变（突然出现又突然消失），体验不好。

### 根本原因

沼泽生物群系的毒雾状态（`hazardStateRatio`）有问题，状态切换导致视觉突变。

### 修复方案

- 移除沼泽生物群系的毒雾状态（`hazardStateRatio: 0`）
- 如果需要水地形，应该用蓝色的、像海面一样的呈现方式，可以稍微连的大一点，但别占据太多，也别阻断玩家前进

### 修改的文件

- `src/systems/terrain/MapGenerator.ts` — 移除毒雾状态

### 对 Cocos/Unity 版的参考建议

- **避免视觉突变**：地形状态切换应该有过渡动画，不能突然出现又突然消失。
- **毒雾类效果要谨慎**：如果实现不好，宁可移除，也不要影响体验。
- **水面应该是蓝色的**：符合玩家的认知，不要用绿色泡泡表示水。

## 9. 砖墙系统：4分块渲染与伤害逻辑

### 问题描述

砖墙应该是4个小砖组成的大砖（2x2，每个16x16，合成一个32x32瓦片），各自独立承受伤害。侧身打的时候可以打掉一块。火力强的时候可以一次打多层。

现在的砖墙是一整块，一次就打掉了。

### 设计方案

1. **数据结构**：
   - 每个32x32瓦片分为4个16x16小砖（左上、右上、左下、右下）
   - 每个小砖独立HP
   - 瓦片整体HP = 4，每打掉一块HP-1

2. **碰撞检测**：
   - 子弹击中瓦片时，根据击中位置判断击中哪块小砖
   - 只对被击中的小砖造成伤害
   - 火力强的子弹可以穿透，一次打多块

3. **渲染**：
   - 根据剩余小砖数量渲染（HP=4全显示，HP=3缺一块，...，HP=0全消失）
   - `MapVisual.renderBrick` 已实现4分块渲染

4. **基地护墙**：
   - 基地周围应该是8块砖（2排x4块，或4x2）
   - 每块砖独立承受伤害，不是一下就能打掉8块

### 当前状态

- ✅ 4分块视觉渲染已实现（`MapVisual.renderBrick`）
- ⚠️ 4分块碰撞和伤害逻辑**尚未实现**（当前还是一整块HP）
- ⚠️ 基地护墙的4分块逻辑**尚未实现**

### 待修改的文件

- `src/game/Tilemap.ts` — 瓦片数据结构支持4分块
- `src/systems/combat/CombatSystem.ts` — 碰撞和伤害逻辑支持4分块
- `src/game/Base.ts` — 护墙逻辑支持4分块

### 对 Cocos/Unity 版的参考建议

- **砖墙4分块是经典设计**：原版坦克大战就是这样的，必须实现。
- **碰撞检测要精确到小砖**：不能只检测瓦片级别，要根据击中位置判断哪块小砖。
- **火力穿透要支持**：高伤害子弹应该能一次打多块小砖。
- **基地护墙要足够厚**：2排x4块=8块砖，给基地足够的保护。

## 10. 基地系统：护墙强化与修复小人

1. 基地护墙太薄，容易被打烂

### 修复方案

   - 基地周围默认生成2排护墙（8块砖）

3. **基地墙变水问题**：
   - 检查基地护墙位置的地图生成，确保不是水
   - 护墙被打烂后应该是空地（`TileType.Empty`），不是水

### 当前状态

- ⚠️ 修复小人同步到2号机**尚未实现**

- **修复小人是基地的重要视觉元素**：必须同步到所有客户端。
- **基地护墙要足够厚**：2排护墙给基地足够的保护。
- **护墙被打烂后应该是空地**：不能变成水或其他地形。

## 11. 道具系统：临时硬墙道具

### 功能描述

新增一种道具，允许玩家使用武器生成一块硬的墙，并放置在那里。切换武器的时候不会消失，但有固定时长会消失（比如30秒）。

这样允许两个玩家各自持自己的两个武器给基地前面放防护保护基地，但是因为他们只能最多放一块，所以两个玩家即使放了两块，也不能保证基地一定安全，但是防护能力会提升。

### 实现方案

1. **模块定义**：`spec_temp_steel_wall`
2. **投射物**：命中后在该位置放置临时硬墙
3. **临时墙管理**：
   - `Tilemap.tempWalls: Map<number, {placedAt, ownerId}>`
   - `placeTempWall(col, row, ownerId)` — 放置临时墙
   - `hasTempWall(col, row)` — 检查是否有临时墙
   - `updateTempWalls(now)` — 更新临时墙（30秒后消失）
   - `getTempWallRemaining(col, row, now)` — 获取剩余时间
4. **每人最多1块**：放置新墙时移除该玩家之前的墙

### 修改的文件

- `src/systems/wand/ModuleRegistry.ts` — 新增模块定义
- `src/systems/wand/WandSystem.ts` — 投射物生成
- `src/systems/combat/CombatSystem.ts` — 投射物命中处理
- `src/game/Tilemap.ts` — 临时墙管理

### 对 Cocos/Unity 版的参考建议

- **临时墙是有趣的战术道具**：给玩家提供防御手段，增加策略深度。
- **每人最多1块**：避免玩家放满整个地图，保持平衡。
- **30秒消失**：临时墙不应该永久存在，要有时间限制。
- **切换武器不消失**：临时墙是独立的游戏对象，不应该和武器绑定。

## 13. 联机大厅：麻将桌座位系统

### 问题描述

联机大厅没有桌子的概念，玩家不知道怎么组队。

### 修复方案

1. **预置桌子**：服务器预置40张桌子（无尽模式20张 + 闯关模式20张），桌子是预留的，加入玩家就占据座位，不需要"开桌"
2. **麻将桌风格座位**：4个座位，可以看到里面几个玩家，也可以看到是加入的人机队友
3. **座位三态轮换**：
   - `open` — 开放，任何玩家可以加入
   - `ai` — AI队友占据
   - `closed` — 关闭，显示为叉号，禁止有其他玩家和AI加入
4. **房主可以调整座位**：点击座位轮换状态（open → ai → closed → open）
5. **邀请功能**：可以通过发链接的形式邀请其他玩家，邀请链接进入对应的桌子和座位

### 修改的文件

- `server/index.mjs` — 预置40张桌子
- `src/main.ts` — 麻将桌风格座位渲染、座位三态轮换、邀请按钮

### 对 Cocos/Unity 版的参考建议

- **桌子是预置的，不是创建的**：服务器预置桌子，玩家加入就占据座位，不需要"开桌"概念。
- **座位状态要明确**：开放/AI/关闭三种状态，房主可以调整。
- **邀请要进入对应座位**：邀请链接应该包含桌子ID和座位ID，玩家点击后直接进入对应位置。
- **关闭座位显示叉号**：明确表示这个位置不允许加入。

## 14. 人机系统：控制权区分与房间内增减

### 问题描述

1. 人机队友默认一直有，玩家不能选择是否加入
2. 2号键盘玩家和AI同时控制2号坦克，AI会抢控制权
3. 真人玩家加入后，AI还在持续控制，导致真人玩家没法玩
4. 人机队友显示在主菜单，位置不对

### 修复方案

1. **控制权区分**：
   - `p2HumanIdleTimer` — 真人玩家输入空闲计时器
   - `p2HumanLocked` — 真人玩家锁定标志
   - 真人玩家有输入时，AI停止控制
   - 真人玩家长时间无输入时，AI可以接管
   - 玩家可以主动选择"被AI接管"

2. **人机队友在房间内增减**：
   - 主菜单移除人机队友选项
   - 在房间内可以增加或减少人机队友
   - 座位三态轮换中可以把座位设为AI

3. **本地双玩家和远程玩家不冲突**：
   - 联机模式下，一个玩家主机就只有一个角色，不存在副手
   - 2号真实玩家不应该被绑定在1号的小键盘那里

### 修改的文件

- `src/framework/GameModeCore.ts` — `p2HumanIdleTimer`/`p2HumanLocked` 控制权区分
- `src/main.ts` — 主菜单移除人机队友选项，房间内人机队友增减
- `src/modes/OnlineHostMode.ts` — `setAICompanion` 公共方法

### 对 Cocos/Unity 版的参考建议

- **人机和真人控制权要明确区分**：真人玩家有输入时，AI必须停止控制。
- **人机队友应该在房间内增减**：不应该在主菜单就决定。
- **联机模式下不存在副手**：每个玩家只有一个角色，不能让本地小键盘和远程输入冲突。
- **AI接管要玩家主动选择**：不能让AI自动抢控制权。

## 附录：共享模块调用关系

```
主机端 (OnlineHostMode)
  ├── Tank.render() → TankVisual.drawTankBody() + drawTankShadow()
  ├── Tilemap.render() → MapVisual.renderTile()
  ├── Base.render() → BaseVisual.renderBase()
  ├── LootSystem.render() → EntityVisual.renderLoot()
  ├── PowerUpSystem.render() → EntityVisual.renderPowerUps()
  └── CombatSystem.renderProjectiles() → EntityVisual.renderProjectiles()

成员端 (RemoteView)
  ├── renderTank() → TankVisual.drawTankBody() + drawTankShadow()
  ├── renderMap() → MapVisual.renderTile()
  ├── renderBase() → BaseVisual.renderBase()
  ├── renderLoot() → EntityVisual.renderLoot()
  ├── renderPowerUps() → EntityVisual.renderPowerUps()
  └── renderProjectiles() → EntityVisual.renderProjectiles()
```

**核心原则**：主机端和成员端调用完全相同的渲染模块，只是数据源不同（主机端是游戏对象，成员端是网络快照）。
